# Політика TSDoc

## Які API потребують TSDoc

Кожен **публічний API** має мати коментар `/** ... */`:

- експортовані функції та стрілкові функції
- експортовані класи
- експортовані інтерфейси та псевдоніми типів
- експортовані константи (`export const`)

**Приватні** (неекспортовані) декларації **не** потребують TSDoc.

## Обов'язкові теґи

| Теґ | Коли обов'язковий |
|---|---|
| `@param` | Для кожного параметра функції |
| `@returns` | Для кожної функції з непорожнім типом повернення |
| `@throws` | Документуйте відомі винятки |
| `@internal` | Для API, не призначених для зовнішнього використання |
| `@remarks` | Додатковий контекст (необов'язково) |
| `@example` | Приклад використання (необов'язково) |

**Не** додавайте анотації типів у `@param` чи `@returns` — TypeScript надає типи самостійно.
**Не** додавайте надлишкових описів, якщо назва параметра й тип є самоочевидними.

## Стиль

```ts
/**
 * Короткий опис. Довше пояснення на наступному рядку, якщо потрібно.
 * @param paramName - Опис параметра.
 * @returns Опис значення, що повертається.
 */
```

- Використовуйте `-` між назвою теґа та його описом.
- Опускайте теґи для самоочевидних параметрів.
- Використовуйте `@internal` замість покладання на фільтр `publicOnly`.

## Як перевірити

```bash
npm run lint          # запускає всі правила ESLint, включно з TSDoc
npm run lint:docs     # те саме (псевдонім для src/**)
npx eslint src/       # явна вказівка шляху
```

## Винятки

- Тестові файли (`tests/`) звільнені від усіх правил TSDoc.
- Файли конфігурації (`eslint.config.js`, `astro.config.mjs`) звільнені.
- Внутрішні допоміжні функції, позначені `@internal`, звільнені від `@param`/`@returns`.
- Стрілкові вирази, функціональні вирази, класові вирази та визначення методів виключені з `require-jsdoc`.

## Політика документування тестів

Тести потребують більше контексту, ніж виробничий код, оскільки вони фіксують крайові випадки, обмеження браузера та історичні регресії, які не є очевидними з однієї назви тесту.

### Коли додавати коментарі

- **Заголовки файлів** — кожен значущий тестовий файл повинен починатися з блоку `/** ... */`, який пояснює, який функціонал тестується, припущення щодо середовища, основні моки та пов'язані вихідні модулі.
- **Коментарі до наборів тестів** — нетривіальні блоки `describe()` повинні мати короткий коментар, якщо назви набору недостатньо.
- **Тести регресії** — документуйте помилку, яку запобігає тест, із зазначенням першопричини або номера задачі, якщо доступно.
- **Моки та фікстури** — пояснюйте, чому реальну реалізацію не можна використовувати в модульному тесті (наприклад, "jsdom не підтримує IndexedDB").
- **Пропущені тести** — кожен `.skip` повинен мати поруч коментар, який пояснює, чому тест пропущено та за якої умови його можна ввімкнути.
- **Неочевидні твердження** — описуйте, що доводить твердження, особливо коли воно включає математичні формули, обмеження порядку або регулярні вирази.

### Коли пропускати коментарі

- Тривіальні твердження, які точно збігаються з назвою тесту.
- Синтаксис — ніколи не коментуйте, що робить код, лише чому він це робить.
- Шаблонні фрази, які повторюють підсумок блоку describe.

### Як перевірити

```bash
# Перевірити, що кожен .skip має причину (структурний тест)
npx vitest run tests/test-documentation.test.ts
```

### Скрипти верифікації

Скрипти в `scripts/verify-*.mjs` вимагають:
- Заголовок файлу `/** ... */`.
- JSDoc для кожної допоміжної функції (`@param`, `@returns`).
- Чітку документацію припущень щодо середовища (URL сервера, порт, версія Playwright).
- Пояснення, яке очищення виконується та що відбувається у разі невдачі.
